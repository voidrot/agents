# Efficient FastAPI

Use this skill for a narrow change in an existing FastAPI application where FastAPI owns the boundary. Preserve the application factory, router registration, dependency graph, and wire contract unless the request changes them. Use `efficient-python` for Python language, resource-lifetime, typing, or asyncio mechanics; `efficient-web-development` for browser-facing behavior and general web/API decisions; `efficient-auth` for authentication and authorization policy; and `efficient-testing` for selecting focused regression coverage.

Do not use this skill to choose an ORM or database design, create schemas automatically, design a new API generally, deploy an application, or configure framework-independent tests. Do not add a package, a compatibility layer, a global service registry, or a background task merely to make a FastAPI change appear complete.

## Workflow

1. **Establish the FastAPI seam.** Read the application factory or application instance, affected router and route declarations, dependency providers and their consumers, Pydantic models, service boundary, and nearest FastAPI tests. Identify the operation's request inputs, output model/status, raised or mapped failures, identity source, resource owner, transaction owner, and startup/shutdown requirement. Inspect installed FastAPI and Pydantic versions plus local conventions before using version-sensitive APIs. Preserve undocumented behavior as an assumption, not a contract.

2. **Keep lifespan ownership application-scoped.** Put resources shared for the application's lifetime in the existing `lifespan` context manager or equivalent established lifecycle boundary; acquire before `yield` and release after it. Keep per-request resources in dependencies and operation-local resources in the operation or service that creates them. Handle partial startup by releasing resources already acquired and propagating the startup failure; do not serve a partially initialized app. Do not perform automatic schema creation, network calls, or unrelated work at import time or in lifespan without an explicit existing requirement. If tests or callers need isolated state, preserve or introduce the smallest existing-style app factory rather than mutating module-global state.

3. **Make dependency boundaries substitutable and cleanup-safe.** Inject request-scoped infrastructure, the authenticated principal, and service collaborators through the existing dependency graph rather than constructing them ad hoc in every handler. Reuse the canonical provider function where overrideability matters: FastAPI dependency overrides are keyed by the original callable. A dependency using `yield` owns cleanup around that yield; preserve its success, exception, rollback, and close behavior rather than duplicating it in handlers. Keep dependencies focused on acquiring or validating one concern. Do not hide business mutations, silent authorization decisions, or transaction commits in a convenience dependency.

4. **Define request and response models as separate wire contracts.** Use request models to validate client input and output models or an explicit `response_model` to constrain serialized data. Do not return persistence objects, internal exceptions, credentials, or write-only fields just because their attributes happen to serialize. Model partial updates so omitted fields remain distinguishable from supplied values; use the installed Pydantic version's documented serialization API when applying them. Keep validation close to the request model, while domain invariants and conflict decisions stay at the service boundary. Change status codes, aliases, default/exclusion behavior, or OpenAPI-visible fields only when the requested contract requires it.

5. **Keep handlers thin and async boundaries honest.** A handler should bind FastAPI inputs, invoke the established service operation, and translate only the expected domain outcomes into the application's HTTP error contract. Match `async def` to async collaborators and `def` to an existing synchronous path; never invoke blocking I/O or long CPU work directly from an async handler. Do not create detached tasks from a request, rely on a response to complete work that has no owner, or swallow cancellation. For the language-level decision, executor use, cancellation, and resource cleanup, follow `efficient-python` rather than inventing a FastAPI-specific workaround.

6. **Integrate authentication at the dependency boundary.** Obtain a validated principal or credentials through the established security dependency, then pass the minimal trusted identity needed by the service or authorization check. Keep credential parsing, challenge headers, and unauthenticated-versus-forbidden mapping consistent with the existing policy; do not treat a client-supplied identifier, role, or claim as authorization. Authorize the requested action and resource before a durable mutation or sensitive response. Do not add token formats, permission models, cookie/CSRF policy, or cryptography here: use `efficient-auth` for those decisions.

7. **Give each business operation one transactional owner.** Keep route functions free of persistence orchestration beyond supplying the injected collaborator. Let the established service or unit-of-work boundary own the full mutation, commit/rollback decision, and translation of expected persistence conflicts into domain outcomes. Preserve atomicity when one request changes multiple records or invokes multiple repositories; do not commit intermediate handler steps. On an unexpected failure, roll back only when the owning boundary requires it, preserve the cause internally, and return the application's safe failure response without exposing infrastructure details. ORM selection, constraints, and schema changes are outside this skill.

8. **Test through FastAPI seams, not production services.** Use a fresh application instance when isolation requires it. Override only the direct provider needed with `app.dependency_overrides`, then clear or restore overrides in fixture teardown so no test leaks its replacement. Supply deterministic fake principals, collaborators, clocks, or request-scoped resources through dependencies; do not patch handlers or contact identity providers. Use `TestClient` as a context manager when the test must exercise lifespan startup and shutdown. For async HTTPX/`ASGITransport` tests, remember that the transport does not trigger lifespan; either test a seam that needs no lifespan or use the repository's already-supported lifecycle arrangement—do not add a lifecycle package solely for a test. Apply `efficient-testing` to decide the smallest meaningful success, validation, authentication, authorization, conflict, or cleanup scenario.

9. **Validate the changed contract.** Run the narrowest repository-supported formatter, type check, and FastAPI-focused test target that reaches the seam. Exercise the changed request and response body, status/error mapping, dependency override isolation, and lifecycle path when affected. Inspect generated OpenAPI or the route declaration when a request/response schema, dependency, or status changes. For an async-boundary change, verify completion, error propagation, and cancellation/cleanup behavior appropriate to the local test stack. Classify a failure before editing again: route registration, dependency resolution/override identity, model validation/serialization, lifespan setup, authentication mapping, transaction ownership, test lifecycle, or unavailable infrastructure. Do not weaken assertions, bypass security dependencies, or add retries to obtain a passing test.

## Completion evidence

Report only what was observed:

- changed FastAPI boundary and preserved or intentionally changed request, response, status, dependency, lifecycle, authentication, and transaction contracts;
- resource and transaction owner, plus cleanup and failure behavior at the affected seam;
- exact targeted commands and manual request/lifecycle checks with results;
- dependency overrides and test-lifespan arrangement used, including isolation/cleanup evidence;
- inspected FastAPI/Pydantic versions and official documentation when a version-sensitive API was used;
- skipped, blocked, or pre-existing failures and the smallest safe next action.

Stop when the requested FastAPI contract has direct evidence. Do not broaden it into a framework migration, generic Python refactor, database redesign, API redesign, deployment change, or test-suite overhaul.
