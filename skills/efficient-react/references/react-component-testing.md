# React component test decisions

Read this only when adding or revising a React component test. Use `efficient-testing` for test scope, scenario selection, isolation, commands, and failure diagnosis; this note only chooses React-specific test seams.

Before writing the test, inspect the package manifest, lockfile, test configuration/setup, and nearby tests. Use the installed runner, rendering and interaction libraries, exact resolved versions, and local helpers/conventions. Do not infer a library API, replace the project setup, or add a dependency for this test.

- **Find elements as users do.** Prefer the installed library's accessible role-and-name query; then use an associated label or user-visible text/value/alternative text when that is the actual contract. Use a test-only identifier only when no accessible or visible contract identifies the element. This priority makes a failing query a useful accessibility signal rather than a DOM-structure assertion.
- **Finish interactions before asserting.** Use the project's highest-fidelity user interaction helper for typing, clicking, keyboard input, and similar gestures. Await or otherwise complete each interaction and wait on the resulting observable condition (for example, changed visible content, accessible state, callback, or request). Do not assert midway through an asynchronous update or synchronize with arbitrary delays.
- **Mock at the network boundary.** When the component's behavior depends on requests, use the repository's established request interception or transport seam so application request code still runs. Configure the response needed for the scenario and make unexpected requests fail when local tooling supports it. Do not substitute child components, React internals, or data hooks merely to avoid exercising that boundary.
- **Match production providers deliberately.** Render with the routing, theme, state, or data providers that the component genuinely requires, using the repository's test wrapper when one exists. Keep the wrapper minimal and create fresh mutable provider state for each test unless the local convention safely manages it.
- **Choose the environment by the claim.** A DOM-level test is appropriate for rendered content, accessible names and states, and ordinary interaction-driven component behavior. Use the installed browser-level test path when the claim depends on actual layout or CSS, viewport behavior, scrolling, native browser APIs, hydration, focus behavior not faithfully represented by the DOM environment, or cross-page integration. A DOM pass is not evidence for those browser-dependent conditions.
