# JavaScript server runtimes and frameworks

## Runtime matrix from current docs

All listed current Logs pages confirm the direct `Sentry.logger` path. The JavaScript pages state support from SDK 9.41.0+, default-enabled from 10.71.0+, with `enableLogs: true` required on older supported versions. Use the package and initialization file for the exact runtime; never infer a bridge across rows.

| Runtime/framework | Direct Logs confirmed | Currently documented logging-library bridges |
|---|---:|---|
| Node.js | Yes | Console (`consoleLoggingIntegration`); Consola (`createConsolaReporter`). The current Node Logs page does **not** document Pino, Winston, or Bunyan as Node-wide bridges. |
| Bun | Yes, on its own current Logs page | Console; Consola. These are confirmed by the Bun page itself, not inferred from Node. Pino/Winston/Bunyan are not documented there. |
| Deno | Yes, on its own current Logs page | Console; Consola. These are confirmed by the Deno page itself, not inferred from Node. Pino/Winston/Bunyan are not documented there. |
| Next.js | Yes across client, server, and edge | Console, Consola, server-side Pino (`pinoIntegration`, 10.18.0+), and Winston (`createSentryWinstonTransport`, 9.13.0+) are explicitly named by current Next.js Logs docs. Bunyan is listed only as upcoming, not supported. |
| React Router Framework mode | Yes, on its own current page | Console; Consola. No Pino/Winston/Bunyan bridge is documented on that Logs page. |
| TanStack Start (React) | Yes, on its own current page | Console; Consola. No Pino/Winston/Bunyan bridge is documented on that Logs page. |

For JavaScript rows, Consola requires 10.12.0+ and console multiple-argument parsing requires 10.13.0+. Re-check current pages before exact configuration because defaults and version gates change.

## Initialization, context, and lifecycle

- **Node/Bun/Deno:** initialize the exact Sentry SDK before importing/constructing loggers that may emit startup records. Do not present Next.js Pino/Winston helpers as general Node, Bun, or Deno support.
- **Next.js:** configure every in-scope runtime separately. Current docs name `instrumentation-client.ts`, `sentry.server.config.ts`, and `sentry.edge.config.ts`; an option in one does not configure the others. Pino is server-side. Keep request data on current/request-isolated scope, never global scope.
- **React Router/TanStack Start:** inspect both browser and server initialization generated by the installed framework/version; configure only the sides in scope and avoid duplicate console capture.
- For serverless/edge/short-lived execution, the cited Logs pages do not establish a universal explicit-flush recipe. Follow exact runtime SDK lifecycle docs if separately verified, await host work where documented, and state that process termination can lose buffered records.

## Safe selection and validation

Prefer direct calls for intentional records. A bridge is appropriate only for an existing listed library and must preserve existing local output. Allowlist levels and primitive/bounded attributes; avoid intentionally attaching secrets, request/response bodies, auth headers, raw URLs, and user text. Expect sensitive-data scrubbing through Sentry server-side rules. Broad Console capture may ingest framework or dependency messages; use a client-side privacy filter only when the user explicitly requests it, as optional defense in depth.

With authorization, test each configured runtime independently using one synthetic correlation value plus a bounded `runtime` attribute. Verify the record came from the expected client/server/edge path and was not duplicated by direct plus Console/Pino/Winston capture. Do not treat a Winston/Pino error event or breadcrumb as proof of Logs ingestion.
