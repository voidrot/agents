# Efficient TypeScript

Use this skill for TypeScript's compile-time contract: compiler configuration, type representations, inference, declarations, module typing, and type-level test evidence. Preserve runtime behavior unless the request explicitly changes it. Use `efficient-javascript` for JavaScript runtime mechanics and `efficient-react` for React-specific work.

## Workflow

1. **Establish the contract and compiler context.** Read the requested behavior, affected public entry points, nearby types and tests, the nearest `tsconfig` files, package scripts, and the installed TypeScript version. Identify the project-reference graph, emitted versus declaration-only outputs, and whether the target is an application or a published library. Treat generated declarations and external input as separate boundaries. Do not copy options, declaration patterns, or utility types from another project without confirming they apply to this compiler and build path.
2. **Classify the change before editing.** Choose the narrowest applicable path:
   - **Compiler configuration:** change the owning config, not every extending config. State which projects inherit it and whether the change affects emit, module resolution, declarations, or checking only.
   - **Internal model:** make states and transitions explicit where a real invariant or consumer requires it; otherwise retain the existing simple representation.
   - **Public boundary:** define the accepted input, returned output, mutability, nullability, error/result behavior, and compatibility expectations before changing exported types.
   - **External data:** keep it `unknown` until a boundary parser proves its shape; TypeScript annotations do not validate JSON, environment values, network data, plugins, or persisted data at runtime.
   - **Declaration or module issue:** identify whether it is a missing runtime dependency, wrong resolution mode, missing upstream types, an incorrect declaration, or an intentional untyped boundary. Do not conceal it with a broad ambient declaration.
3. **Set strictness deliberately.** For new TypeScript code, enable `strict` unless an explicit compatibility constraint prevents it. Preserve explicit null and undefined cases rather than suppressing errors with non-null assertions or broad casts. Consider `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` when their stricter semantics match the domain and the affected code has been audited; introduce them in a scoped, measurable migration when they would surface substantial existing debt. Do not disable strict options globally to pass one file. If a migration must be staged, isolate the temporary exception, name the remaining failures, and leave a removal condition.
4. **Model data for the operations that consume it.** Prefer a discriminated union for variants with different required fields, `readonly` where mutation is not part of the contract, and distinct domain types when similarly shaped values are commonly confused. Represent absence explicitly with `undefined`, `null`, or an explicit variant according to the existing boundary contract; do not treat optional properties as interchangeable with values that may be `undefined`. Keep one source of truth for derived state. Do not add brands, recursive conditional types, or a hierarchy of wrappers unless they prevent a concrete error or make a required operation total.
5. **Let inference work, then constrain it at ownership boundaries.** Prefer clear values, parameters, and return types over redundant annotations. Add an explicit type when it documents a public contract, prevents an undesired widening or inference leak, anchors an empty/container value, or gives a stable declaration surface. Prefer `satisfies` when checking a value against a shape while retaining its inferred literals. Derive a local view from the owning type with built-in utility types or indexed access before creating a duplicate shape. Avoid `any`; if an intentionally unsafe interoperation is unavoidable, contain it at one documented boundary and convert it to a checked type immediately.
6. **Narrow from evidence.** Use control-flow narrowing, equality checks, discriminants, `typeof`, `instanceof`, or property-presence checks that match the actual runtime representation. Write a user-defined guard or assertion function only when it verifies every fact it claims; a type predicate is part of the safety boundary, not a naming convention. Make switches over maintained discriminated unions exhaustive with a `never` check. Do not use `as`, `!`, or a declared type predicate to silence a compiler error unless a narrow, locally documented invariant has already been established and cannot be represented otherwise.
7. **Design generics for callers, not type-system display.** Start with the concrete use cases. Use the fewest type parameters and constraints that preserve the relationship callers need. Prefer a generic that returns a relationship already present in its inputs over overloads, conditional types, or template-literal types. Add overloads only when each call shape has a distinct, understandable result and a union-based signature would lose required inference. Stop before a helper needs intricate conditional recursion, distributed-union tricks, or error messages callers cannot act on; use a simpler API or a concrete boundary instead.
8. **Choose module and declaration boundaries truthfully.** Follow the project's configured module and resolution mode. Use `import type` and `export type` for type-only dependencies when the compiler configuration or project convention requires an unambiguous type-only boundary. For a library, export only deliberate stable types and ensure declarations describe emitted public values; do not leak internal types through exported signatures. Add an ambient module declaration only for a verified untyped dependency or asset boundary, scope it to the exact module pattern, and declare only the runtime surface that actually exists. Prefer correcting package exports, resolution configuration, or upstream types over `declare module "*"`, broad globals, or duplicate third-party declarations.
9. **Validate at the right boundary.** Reuse the repository's established parser or schema mechanism when present; do not add a validation dependency for a one-off shape without a concrete need. Convert validated input to a named domain type and pass that type inward. On invalid input, preserve the existing error/result contract and make the failure actionable enough for the caller. Do not claim that a compile-only check protects a runtime boundary.
10. **Verify the changed contract.** Run the repository's narrowest type-check command that reaches the owning config, then the affected build or declaration-emission command when configuration, public types, imports, or declarations changed. Run lint only if it checks the affected TypeScript boundary. Use `efficient-testing` for focused runtime or regression tests. Add a compile-time test only when the type relationship is public, subtle, or has previously regressed; check both an accepted use and, where supported by the project's test tooling, a rejected use. Keep type tests separate from runtime tests when their runners or failure semantics differ.
11. **Diagnose failures from the first unsound boundary.** Reduce the error to the smallest failing call, export, config, or declaration. Inspect the inferred type, compiler option and resolution trace only as needed; then test one falsifiable cause at a time: wrong model, missing narrowing, unwanted widening, incompatible public change, wrong project config, or false declaration. Fix the source boundary rather than adding a cast, loosening a type, disabling an option, or changing a test expectation. If compiler, package, or generated-code prerequisites prevent verification, report the exact command, failure, affected contract, and smallest next action.

## Decision rules

- Preserve a public type unless a breaking change is requested. If a widening or narrowing is necessary, inspect direct consumers and version the change according to repository policy.
- Keep internal types near the code that owns their invariant. Move a type to a shared module only when multiple independent consumers need the same stable contract.
- Prefer `type` or `interface` according to local convention; choose based on needed capabilities, not a universal rule. Use `type` for unions and intersections naturally; use an interface when declaration merging or an extendable object contract is explicitly needed.
- Avoid optional-property bags for mutually exclusive variants. Do not replace a straightforward union with a class hierarchy or a generic abstraction without a demonstrated consumer benefit.
- Measure type-check or editor degradation before optimizing type-level performance. Simplify a confirmed expensive type or reduce its public expansion; do not remove useful checking based on assumed compiler cost.
- Do not add `skipLibCheck`, path aliases, ambient globals, or module shims as local-error fixes without analyzing their project-wide effect.

## Completion evidence

Report only completed evidence:

- affected compiler config, type boundary, exports, declarations, and any runtime-validation ownership;
- strictness or compatibility choice, including temporary exceptions and their removal condition;
- focused type-check, build/declaration, lint, runtime-test, and type-test commands actually run with results;
- accepted and rejected type scenarios covered when a type test was added;
- skipped or blocked verification, its exact failure, and remaining risk.

Stop when the requested TypeScript contract is sound, conventional for the repository, and verified at its owning boundary. Do not broaden the change into JavaScript runtime, framework, or generic refactoring work.
