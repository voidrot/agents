# Efficient Auth

Use this skill for an application-side identity or access-control change: login, logout, a protected endpoint, session or token handling, an OAuth/OIDC callback, account recovery, or an authorization failure. Make the smallest change that preserves a server-enforced boundary. Authentication establishes an actor; authorization decides that actor's permitted action on a specific resource. Never let a client-side check, a role/tenant/owner value supplied by the client, or a successfully decoded credential substitute for server-side authorization.

Do not use this skill for identity-provider administration, user/account/privacy/security configuration that needs separate authorization, product decisions about who should have access, or generic browser and application implementation. Use `efficient-web-development` when a browser-facing flow beyond its auth boundary needs implementation. Use `efficient-testing` for focused regression coverage. Use `github-actions` only when an auth-related CI workflow or its secret boundary changes.

## Workflow

1. **Establish the boundary before editing.** Read the request, existing auth middleware and routes, credential/session storage, authorization checks, configuration, tests, and the affected resource access path. State the actor, entry point, credential type, resource and action, trust boundary, success result, and safe failures. Trace identity from request through credential validation to the resource query or mutation. Keep existing product access policy and identity-provider configuration unchanged; if either is missing, ambiguous, or must change, stop and request the responsible decision.

2. **Choose only the credential model the requirements justify.** Preserve the established mechanism when it satisfies the path.
   - Use a server-managed session when the application needs a browser login with server-side revocation or state and an existing session boundary supports it.
   - Add OAuth/OIDC only when delegated or external identity, an existing provider integration, or a stated interoperability requirement requires it. Use the documented flow and official documentation for the installed library/provider version; do not invent provider setup or accept a callback without validating the flow's binding data.
   - Use a bearer token or JWT only when a stated client/API or distributed-validation requirement needs it. A JWT is not authorization by itself: verify it with the configured trusted key material and enforce the expected issuer, audience, expiry, and other applicable claims before using its subject.
   Do not introduce a second mechanism, custom cryptography, a token refresh system, or a revocation store merely because it is common. If no supported choice meets the requirement, fail safely and obtain a design decision.

3. **Implement the credential lifecycle explicitly.** Create credentials only after the established identity verification succeeds. Use established, vetted password/session/token facilities; never store or log plaintext passwords, raw recovery secrets, session identifiers, access tokens, or signing secrets. Give credentials bounded expiry appropriate to the existing contract and reject malformed, expired, revoked, or otherwise invalid credentials without partial authentication. Rotate or renew only where the existing contract requires it. On logout, invalidate the server-side session or otherwise perform the established credential invalidation, clear the client credential with matching cookie scope where applicable, and make repeated logout safe. For recovery, use an unpredictable, single-use, expiring secret; store only a safe verifier where the existing design permits, consume it atomically, and return account-enumeration-safe responses when that is the established policy. Limit post-login or recovery redirects to validated local or allowlisted destinations.

4. **Enforce authorization next to the protected operation.** Authenticate at the server boundary, then authorize the action and the specific resource before reading sensitive data or mutating state. Derive the actor, tenant, role, and ownership scope from the validated server-side identity and trusted resource data, not request fields. Scope resource lookups and mutations by the authorized tenant/owner where possible; otherwise make an explicit ownership or permission decision before the operation. Default to denial when identity, scope, or a required permission is absent. Apply the check to every equivalent route, background entry point, and bulk operation that reaches the resource. Do not rely on hidden UI, client routing, identifier obscurity, or a role claim that has not been validated under the established trust model.

5. **Protect browser credential boundaries deliberately.** For cookie-carried credentials, set `Secure` on HTTPS deployments, `HttpOnly` unless browser script demonstrably needs the cookie, and an explicit `SameSite`, path, and host/domain scope no broader than required. Treat state-changing cookie-authenticated requests as CSRF-sensitive: preserve the established CSRF defense and validate the relevant origin/referer boundary where that contract uses it; never make a state change through `GET`. A cookie attribute alone is not a reason to remove CSRF protection. Do not enable credentialed cross-origin requests, loosen CORS/origin checks, or add cross-site cookie scope to make a flow work. Stop for a security/API decision when cross-origin credentials, redirects, embedded contexts, or a new browser origin are required.

6. **Keep secrets and errors contained.** Obtain keys, client secrets, and session secrets through the repository's approved secret/configuration mechanism; validate required configuration at startup or the narrowest safe initialization boundary. Do not commit secrets, put them in URLs, browser storage, source maps, client bundles, test fixtures, logs, traces, error messages, or command-line arguments. Redact sensitive fields in diagnostics. Return a stable, user-safe response that distinguishes a correctable login/input failure from unauthenticated, forbidden, absent, conflict, and unexpected outcomes only as far as the existing contract permits; never disclose credential validity, account existence, policy internals, or stack traces unnecessarily.

7. **Validate the affected attack and lifecycle paths.** First run the narrowest existing checks. Add or update only the focused test cases supported by the changed contract, using disposable identities, data, and fake secrets. At minimum, prove the intended authenticated success path and an unauthenticated denial. Also prove the relevant authorization boundary—for example, a different user or tenant cannot access or mutate the resource—and the changed lifecycle path, such as expiry, logout invalidation, recovery single use, or OAuth/OIDC callback binding. Exercise cookie/CSRF/origin rejection when that boundary changed. Inspect responses and safe logs for credential or secret disclosure. Do not use real credentials, production identities, or a live provider to obtain passing evidence. If an installed auth library API, protocol behavior, or browser behavior is version-sensitive, verify the exact usage against its official documentation before editing and report that source.

8. **Diagnose failures without weakening the boundary.** Preserve safe request/response metadata, credential state classification, relevant configuration presence (not values), and the first authorization decision that differs from expectation. Distinguish authentication failure, claim/session validation failure, authorization/ownership failure, CSRF/origin rejection, redirect validation, expired/revoked lifecycle state, and unavailable test infrastructure. Change one evidenced cause at a time. Never bypass middleware, disable CSRF, trust a client claim, extend lifetime, return a broader role, add a wildcard origin, or log a secret to make a test or integration pass.

## Completion evidence

Report only observed evidence:

- the changed entry point, credential lifecycle, server-side authorization rule, and resource/tenant ownership boundary;
- the selected mechanism and the requirement or existing contract that justified it, plus mechanisms intentionally not introduced;
- cookie, CSRF, origin, redirect, secret-handling, expiry, logout, or recovery behavior examined when applicable;
- focused commands or manual steps, their results, fixtures/prerequisites, and any official documentation consulted for version-sensitive behavior;
- skipped, blocked, inconclusive, or pre-existing failures, with the smallest safe next action.

Stop when the affected authentication and authorization boundary has direct evidence. Do not broaden the change into provider administration, access-policy redesign, generic security hardening, or unrelated web work.
